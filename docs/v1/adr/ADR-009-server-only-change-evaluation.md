## 1 상태

**Accepted** (2026-09-24, 소유자 CJH).

## 2 맥락

- 기존 임상 산정은 승인 정책이 없으면 '산정 준비 중'(`UNSCORED`)을 돌려준다(dfet:functions/src/clinical/scoring.js:6-11).
- 판정(4상태)은 트레이너 앱(Swift)과 회원 앱(Dart) 모두에서 표시된다. 두 곳에 구현하면 어긋나고 정책 감사가 어렵다.
- MDC 정책은 승인·활성·롤백 대상이다(AD-04, §12.4).

## 3 결정

1. §7.5 판정(`judge()`)은 `functions/src/change/evaluateChange.js` 한 곳에만 구현하고 `contracts/vectors/change-eval.v1.json`(T01~T25)으로 CI에서 검증한다.
2. 트레이너 앱과 회원 앱은 `changeStatus`, `reasonCode`, `policyVersion`, `mdcSource`를 **표시만** 한다. 판정 로직과 MDC 상수를 코드에 두지 않는다(static guard).
3. P3 전 스냅샷과 highlight는 모두 `changeStatus = 'pendingPolicy'`로 저장하고, 화면은 '산정 준비 중'을 보인다(AC-C-03.1).
4. `seriesBreak`(conditionKey 비교, §7.4)는 판정이 아닌 표시 규칙이므로 TrainerDomain과 Dart 공통 규칙으로 구현하고 같은 벡터로 검증한다(DF-216).
5. 트레이너 앱이 오프라인이면 판정 자리에 '온라인 필요'를 표시한다.

## 4 결과

**좋아지는 점**
- 판정이 한 벌이라 정책 승인·롤백·재현이 가능하다.
- 판정 전 기간에도 값과 추이는 보여 준다.

**비용·위험**
- P3 판정은 온라인 전용이다.
- 스냅샷이 저장 시점 판정을 담으므로 정책이 바뀌면 이전 스냅샷과 새 판정이 다를 수 있다(policyVersion으로 구분).

**후속 작업**
- DF-216 seriesBreak 공통 규칙, DF-217 pendingPolicy 스냅샷, DF-380 엔진, DF-381 연동, DF-382·DF-383 표시.

## 5 대안

| 대안 | 장점 | 채택하지 않은 이유 |
|---|---|---|
| Swift·Dart 각각 구현 | 오프라인 판정 | 두 벌이 어긋나고 감사 불가 |
| 기기 안에서 판정 | 지연 없음 | 정책 승인·롤백·재현 추적 불가 |
