## 1 상태

**Accepted** (2026-09-24, 소유자 CJH). 허용 목록·서버 집계 원칙은 확정이다. 전송 제공자(Firebase Analytics)와 크래시 SDK 도입은 G-09 처리방침 공개 때 확인하며, 그 전에는 전송하지 않는다.

## 2 맥락

- M-01(기록 시간), M-02, M-08, M-11은 이벤트 측정이 필요하다(§5.3).
- 분석 SDK는 국외(미국) 처리를 전제로 한다(AS-19). 처리방침 공개(G-09) 전에는 국외 이전을 할 수 없다.
- 기존 원칙: 건강 수치·이름·메모를 이벤트에 넣지 않는다(PRD §5.5, dfet:docs/UI_UX_REDESIGN_PRD_2026.md:434-447).

## 3 결정

1. 이벤트명과 속성은 `contracts/analytics-events.v1.json` 허용 목록에 있는 것만 보낸다. `TrainerAnalytics`가 생성 enum으로만 `track`하며 목록 밖 속성은 단위 테스트에서 실패한다.
2. 시간은 `elapsed_band`로만 보낸다. `session_id`는 회원과 연결되지 않는 난수다.
3. 보내지 않는 것: 건강 수치, 판정 결과, 동의 유형, 이름·이메일, 자유 메모, 사진·필기·Storage 경로, 통증 부위, uid.
4. 회원 단위 결합이 필요한 지표는 `aggregateOpsMetrics`가 `opsMetrics/{isoWeek}`에 건수·비율로 계산한다.
5. 싱크는 프로토콜이다. G-09 전에는 `DebugSink`(os.Logger 디버그 레벨, 네트워크 전송 없음)만 쓰고 FirebaseAnalytics 제품을 링크하지 않는다. G-09 뒤 `FirebaseAnalyticsSink`(FirebaseData)로 바꾼다(AS-DEV-07).
6. 로그는 `os.Logger`와 privacy 옵션을 쓴다. 식별자는 `.private(mask: .hash)`, 값·메모·경로는 기록하지 않는다.
7. 이벤트명과 audit action은 금지어 린트 대상이다.
8. 동의 변경은 이벤트로 보내지 않고 auditLogs `consentChanged`에만 남긴다.

## 4 결과

**좋아지는 점**
- 개인정보가 분석 경로로 새지 않음을 테스트로 보장한다.
- G-09 전에도 개발·측정 코드를 완성해 둘 수 있다(DebugSink로 로컬 확인).

**비용·위험**
- G-09 전 자체 사용 기간(P1a 초반)의 M-01은 실기기 로그와 수동 측정에 의존한다.
- 서버 집계 지표는 주 단위라 즉시 확인이 어렵다.

**후속 작업**
- DF-033 레지스트리, DF-126 전송기와 M-01·M-02 이벤트, DF-137·DF-224 서버 집계.

## 5 대안

| 대안 | 장점 | 채택하지 않은 이유 |
|---|---|---|
| 자체 Firestore 이벤트 수집 | 국외 이전 없음 | 개발 비용(Q-DEV-01로 재검토) |
| 수집하지 않음 | 위험 최소 | M-01 측정 불가 |
| 자유 속성 허용 | 유연 | 개인정보 유입을 막을 수 없음 |

§5.3, §5.5, NFR-10, NFR-11, AS-19, F-PRIV-06.3, M-01, M-02, M-08, M-11, G-09. 설계 반영 위치: [V1-04 §20](../04_ARCHITECTURE.md#20-관측-가능성과-로깅), 이벤트 레지스트리는 [V1-12](../12_COPY_ANALYTICS_AND_LINT.md).

## 7 재검토 조건

- G-09에서 국외 이전 공개가 불가하다고 결론 나면 자체 Firestore 이벤트 수집(Q-DEV-01)으로 바꾼다.
- 크래시 SDK 도입 여부를 G-09와 함께 결정하고 이 ADR에 기록한다.
