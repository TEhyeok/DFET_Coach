## 1 이 문서의 원칙

- **문서에만 둔다.** 이 문서의 카드는 스프린트에 넣지 않는다. 마일스톤은 'V2(보류)'이고 점수는 0(미추정)이다. 이슈를 만들 때도 `phase/V2`, `status/blocked` 라벨을 붙여 보드의 Backlog 열 밖에 둔다. 단, `status/` 라벨은 이슈당 0 또는 1개이므로([02 §3](../02_PRODUCT_BACKLOG.md#3-라벨-체계)) 소유자가 아직 받아들이지 않은 제안 카드(DF-506~DF-508)에는 `status/needs-decision`만 붙이고, 받아들이면 `status/blocked`로 바꾼다([tool/backlog/README](../../../tool/backlog/README.md)).
- **범위를 늘리지 않는다.** PRD v1이 V2라고 적은 항목(§12.1 V2 행: InBody API, HealthKit, AI 초안, 임상 모드·특수검사, LiDAR 정식화, 4축 편입 재검토)만 스파인 키(DF-500~DF-505)를 가진다. 그 밖에 PRD가 '향후', 'V2 이후'라고만 적은 것은 §4 추가 제안이나 §7 목록에 둔다.
- **재검토 조건이 먼저다.** 각 카드는 '진입(재검토) 조건'을 모두 만족하고, 별도 PRD(또는 PRD v1.x 개정)가 승인된 뒤에만 스파이크를 연다(PRD §12.1 V2 진입: 'P3 종료와 별도 PRD 승인').
- **v1 코드는 V2를 위해 미리 만들지 않는다.** v1이 미리 해 둔 것은 PRD가 명시한 '수용 설계'(§5)뿐이다. 그 밖의 준비 코드(빈 플래그 키, 사용하지 않는 권한, 숨긴 화면)는 만들지 않는다(§6).
- **가정.** 이 문서의 가정은 `ASM-V2-NN`이며 번호는 이 문서(V1-02-V2) 안에서만 유일하다.

| PRD refs | F-BC-04.1~04.3, D5, RISK-08, F-LINK-04.3, AC-BC-04.1, 부록 A(`segmentalLeanMassKg`, `phaseAngleDeg`) |

**사용자 스토리(목표 상태)**
트레이너로서, 센터 InBody 기기의 측정 결과가 손으로 옮겨 적지 않아도 회원 기록에 들어오기를 원한다. 그래야 입력 실수가 줄고 부위별 근육량 같은 추가 지표도 볼 수 있다.

**왜 보류인가**
- 센터 계정·API-KEY 승인 절차와 요금에 대한 공개 자료가 없다(F-BC-04.2, RISK-08).
- v1은 수기 입력과 결과지 사진으로 충분하다고 가정한다(AS-01, D5).

**진입(재검토) 조건** — 모두 충족
- [ ] LookinBody Web API 사용 승인, 센터 계정, API-KEY, 요금 조건을 서면으로 확보(RISK-08)
- [ ] InBody 쪽 데이터 처리 위치·위탁 관계를 처리방침에 반영할 수 있는지 법률 검토(G-09 갱신)
- [ ] P1a 종료 검토에서 AS-01(수기 입력으로 충분)이 흔들렸다는 근거(입력 시간·오류) 또는 센터 요구
- [ ] 별도 PRD(또는 PRD 개정) 승인

**v1에서 준비된 것**
- `bodyCompositionRecords`에 `source=inbodyApi`, `externalId`, `idempotencyKey`, `rawPath` 필드 자리(§9.2, F-BC-04.1). v1 규칙은 클라이언트에 `source=='manualEntry'`만 허용한다(§9.4). 필드 존재 검증은 AC-BC-04.1 v1 부분(P0 DF-006).
- `memberAliases.system`에 `inbody` 값, `externalId = {LookinBody 계정}:{UserID}`(전화번호 금지, F-LINK-04.3).
- 원문 보관·멱등 수집 패턴: dfet:functions/src/clinical/ingestion.js:83-102, 수집 종류 목록: dfet:functions/src/clinical/constants.js:42(`INGESTION_TYPES = ['gut', 'blood']`).

**착수 시 첫 작업(제안)**
- 스파이크(타임박스 3일): 샌드박스 계정으로 응답 스키마를 확인하고, v1 `values` 키 매핑표와 `segmentalLeanMassKg` 측면·부위 정의(부록 A.1 'v2에서 정의')를 만든다.
- 예상 영향 범위: `functions/src/clinical/constants.js`(`bodycomp` 추가), 새 정규화 모듈, `clinical-ingest/bodycomp/{jobId}/payload.json` 경로(§9.5), 멱등 테스트(AC-BC-04.1 v2 부분), admin_web 별칭 매핑 화면.

**v1 동안 금지** `INGESTION_TYPES`에 `bodycomp`를 넣지 않는다. 트레이너 앱·회원 앱에 InBody 연결 설정 화면을 만들지 않는다.

**열린 질문** 한 센터에 여러 InBody 계정이 있을 때 `externalId` 유일성 단위(F-LINK-04.3 '매장 단위 유일').

**사용자 스토리(목표 상태)**
회원으로서, 집에서 잰 체중·체지방률을 앱이 건강 앱에서 읽어 트레이너 기록 옆에 참고로 보여 주기를 원한다.

**왜 보류인가**
- HealthKit 체성분 타입은 체중·BMI·체지방률·제지방량·키·허리둘레뿐이고 골격근량이 없다(§6.2 표).
- HealthKit 샘플은 측정 조건 메타를 보장하지 않아 항상 판정 불가(`conditionMismatch`)다(F-BC-05.1). 허리둘레는 방법이 불명이라 `selfReport`로 받고 `tape`와 섞지 않는다.

**진입(재검토) 조건**
- [ ] 제지방량(`leanBodyMass`) 등 새 지표를 부록 A에 먼저 등재(§6.2 표 마지막 행)
- [ ] 회원 자가 측정값의 출처 등급·표시 규칙 결정(§4의 DF-506, Q-12와 함께)
- [ ] 동의 ② 문서가 HealthKit 출처 항목을 포함하도록 개정 가능(G-04 갱신)
- [ ] 별도 PRD 승인

**v1에서 준비된 것** `bodyCompositionRecords.source` enum에 `healthKit` 값 자리(§9.2). 출처 등급 분리 규칙(C-02)과 seriesBreak(§7.4)는 이미 다른 출처를 한 선에 잇지 않게 한다.

**착수 시 첫 작업(제안)** 스파이크: 회원 앱(Flutter, iOS 15.5) HealthKit 플러그인 선택과 권한 문구, `selfReport` 시리즈 표시 시안. 예상 영향: `ios/Runner/Info.plist` `NSHealthShareUsageDescription`, entitlements, 회원 앱 저장소 새 파일.

**v1 동안 금지** 회원 앱 Info.plist에 `NSHealth*` 키나 HealthKit entitlement를 넣지 않는다(현재 없음, F-BC-05.1).

트레이너로서, 음성·필기에서 O 수치 후보를 뽑아 확인 칩으로 제안받고 싶다. 그래야 수치 누락이 줄고, 확정은 여전히 내가 한다.

**왜 보류인가**
- 효과 근거가 제한적이다(8시간당 16분 절감, 문헌값). PT 특화 정확도의 독립 근거가 없다(F-SOAP-08.3).

**진입(재검토) 조건**
- [ ] P1a·P1b에서 측정한 M-01·M-11·M-G5와 O 수치 누락률 기준선 확보(효과 목표는 누락 감소, F-SOAP-08.3)

- [ ] 식약처 분류 영향 검토(G-05 계열 재확인)
- [ ] 별도 PRD 승인

**v1에서 준비된 것** 없음. PRD는 v1에서 구현하지 않는다고 적었다(F-SOAP-08 서두). 확정은 늘 트레이너가 한다는 원칙(§3.6, F-SOAP-04)과 스냅샷의 출처 추적 필드는 v1 구조로 이미 있다.

**착수 시 첫 작업(제안)** 스파이크: 합성 세션 음성·필기 샘플로 추출 정확도와 칩 UX 시안. 수락된 값에 `extractionEngine{name, version}`을 기록하는 스키마 초안(F-SOAP-08.2).

**v1 동안 금지** 트레이너 앱에 마이크 권한, 음성 녹음, 외부 모델 호출 코드를 넣지 않는다. 회원 앱에 있는 `firebase_ai` 의존성(dfet:pubspec.yaml:47)을 SOAP·체형 기능에 쓰지 않는다.
